# 개발 과정 명세 (개발 하네스)

oxygen-pi-system 을 만드는 방식이다: 무엇을 만들지(명세), 지금 어디까지 왔는지(진행판), 다음으로 넘어가도 되는지(전이 조건), 누가 어떤 순서로 일하는지(작업 루프), 같은 실수를 어떻게 다시 하지 않는지(개선 루프).
진행 상태: [진행판](dev-board.md) 의 `dev-process` 행.

요청 (사용자, 2026-11-12): 요구사항을 명세로 정의하고, 명세마다 상태를 두어 정해진 조건(테스트 · 실측 · 사용자 승인)을 만족할 때만 다음 단계로 옮기며, 구현 · 평가 에이전트들이 검증 실패와 회고를 거쳐 스스로 나아지는 작업 루프를 만든다.

결정된 사항 (사용자, 2026-11-12: "권장안대로 전부 승인할게, 적용하고 커밋해줘")
- §9 의 D1~D10 을 모두 권장안 (a) 로 정했다. §8 의 A1~A15 를 적용했다 (`dev-process/1`).
- 위임할 때의 넘김 내용과 결과 검토는 `.claude/rules/delegation-rule.md` 가 기준이다 (D10). 이 문서는 진행판에 남길 것(상태 · 증거 · 실패 분류)을 정한다.

이미 쓰고 있는 방식(명세 먼저 · 사용자 승인 후 구현 · 확인받은 캡처가 명세 · 부모를 거치는 역할 분담 · 실측 기록)을 그대로 바탕으로 한다. 새로 더하는 것은 상태 이름과 전이 조건, 진행판 하나, 넘김 양식, 회고를 검사로 바꾸는 규칙이다.

## 1. 명세 형식과 위치

요구사항 하나는 명세 하나(`docs/<영역>-spec.md`)이거나, 기존 명세의 절 하나다.

| 경우 | 위치 | 예 |
| --- | --- | --- |
| 새 기능 · 새 화면 묶음 | 새 파일 `docs/<영역>-spec.md` | `docs/monitor-spec.md` |
| 기존 명세의 규칙을 넓히는 것 | 그 명세의 절 (`##` 또는 `###`) | `docs/tui-spec.md` §11 "Anthropic 워크스페이스" |
| 사용자 보고로 동작을 바꾸는 버그 수정 | 그 기능의 명세에 절 하나 (명세가 없으면 새 파일, §9 D3) | oxy-flow 세션 단위 기록 |
| 동작이 바뀌지 않는 버그 수정 (명세대로 고침) | 명세 없음. 진행판 메모와 커밋 메시지 | `46a5128` 손자 프로세스 정리 |

명세에 담을 것 (순서는 `docs/monitor-spec.md` 를 따른다):

```
# <제목>

<무엇을 하는지 한두 줄>
진행 상태: [진행판](dev-board.md) 의 `<id>` 행.

요청 (사용자, YYYY-MM-DD): <사용자 요청 원문의 요지>
결정된 사항 (사용자, YYYY-MM-DD)
- <사용자가 정한 것. 승인할 때마다 날짜와 함께 더한다>

## 1 … n. 본문 (확정 사항: 규칙 · 형식 · 화면 · 문구)
- 구현 (k단계, YYYY-MM-DD): <구현이 끝난 뒤 어디에 어떻게 했는지>
- 실측 (YYYY-MM-DD, <환경: pi 버전 · 창 크기 · 연결/모델>): <결과>. 증거: <커밋 · 캡처 경로 · 로그>

## n+1. 확인된 사실 (실측 표, 있으면)

## n+2. 구현 순서와 확인 방법
1. <단계> (§k) — 자동 검증: <§6 의 명령> / 실측: <방법> [승인 필요: 과금 LLM · 사용자 화면 · 실제 설치본]
완료 조건: 모든 단계 + <명세 전체의 마무리 실측>

## n+3. 정할 것
- 없음
- (또는) D1 <질문> — (a) … (b) … 권장 (a): <이유>
```

- 상태는 명세에 쓰지 않는다. 명세에는 진행판 행을 가리키는 한 줄만 둔다 (§3). 결정 · 구현 위치 · 실측 기록은 지금처럼 명세 본문에 둔다.
- "구현 순서와 확인 방법"의 각 줄이 그 단계의 전이 조건이다 (§2). 확인 방법이 없는 단계는 두지 않는다.
- 기존 명세의 절로 쓸 때는 그 절 끝에 `구현 순서와 확인 방법` · `정할 것` 을 작은 목록으로 둔다.
- 사용자가 확인한 캡처는 그 자체가 명세다. 명세에는 확인한 날짜와 화면 이름, 핵심 줄을 적는다 (캡처 원본을 어디에 둘지는 §9 D5).
- 문체는 명세체(`~한다`)이고 화면 문구 인용은 원문 그대로다.

## 2. 상태와 전이

### 상태

명세의 상태와 단계(구현 순서의 한 줄)의 상태를 따로 둔다. 상태마다 다음에 움직일 사람이 정해져 있다.

| 명세 상태 | 뜻 | 다음에 움직이는 사람 |
| --- | --- | --- |
| `초안` | 쓰는 중이거나 정할 것이 남음. 구현을 넘기지 않는다 | 부모 · harness-engineer (작성), 사용자 (결정) |
| `승인` | 정할 것이 없고 사용자가 승인함. 아직 넘긴 단계가 없음 | 부모 (첫 단계를 넘김) |
| `구현` | 단계 하나 이상이 `구현` 또는 `검증` | 담당 에이전트 |
| `검증` | 모든 단계의 자동 검증이 끝나고 실측 · 마무리 실측만 남음 | 부모 · 담당 (실측), 사용자 (키 · 화면 확인) |
| `완료` | 완료 조건의 실측까지 끝나고 실측 기록이 명세에 있음 | 없음 (커밋 · 설치본은 따로, §2 끝) |
| `보류` | 사용자가 멈춤. 사용자가 다시 요청할 때만 멈추기 전 상태로 돌아간다 | 사용자 |

| 단계 상태 | 뜻 |
| --- | --- |
| `예정` | 아직 넘기지 않음 (명세가 `초안` 으로 돌아가 다시 해야 하는 단계도 여기로) |
| `구현` | 담당 에이전트에게 넘김 |
| `검증` | 자동 검증 통과, 실측 남음 |
| `완료` | 확인 방법의 실측 통과, 실측 기록 있음 |

막힌 이유(사용자 키, 외부 한도, 사용자 결정)는 상태가 아니라 진행판의 `대기` 열에 쓴다. 상태는 그대로 두고, 무엇을 · 누가 풀어야 하는지 적는다.

### 전이

| # | 전이 | 조건 | 증거 (남기는 곳) | 실행 |
| --- | --- | --- | --- | --- |
| T1 | (없음) → `초안` | 사용자 요청 · 사용자 보고 | 진행판에 행 추가. 명세의 `요청 (사용자, 날짜)` | 부모 |
| T2 | `초안` → `승인` | 명세의 `정할 것` 이 `없음` 이고, 사용자가 메시지로 승인함 | 명세의 `결정된 사항 (사용자, 날짜)`, 진행판 `승인` 열에 날짜 | 부모만. 에이전트의 보고는 승인이 아니다 |
| T3 | `승인` → `구현` | 구현 순서의 다음 단계를 담당에게 넘김 (§4 넘김과 보고) | 진행판 단계 행 `구현`, 담당 · 날짜 | 부모 |
| T3b | `승인` → `검증` | 명세보다 구현이 먼저 있던 경우 (사후 명세). 자동 검증을 지금 코드로 다시 돌려 통과 | 단계 행에 명령 · 결과 줄 · 기준 rev | 부모 |
| T4 | 단계 `구현` → `검증` | 바꾼 곳에 맞는 자동 검증(§6 표)이 모두 통과 + 저장소 위생 검사 통과 | 단계 행 `자동 검증` 열: 명령 이름 · 결과 줄(`# fail 0`, `E2E 통과` …) · 기준(`HEAD f2b2878 + 미커밋` 또는 커밋) | 담당이 보고, 부모가 기록 |
| T5 | 단계 `검증` → `완료` | 그 단계 확인 방법의 실측 통과. 승인 지점이 들어가면(과금 LLM · 사용자 화면 · 실제 설치본) 사용자 승인을 받은 뒤 | 명세 본문의 `실측 (날짜, 환경): …` 한 줄 + 진행판 `실측` · `증거` 열 | 부모 |
| T6 | 명세 `구현`/`검증` → `완료` | 모든 단계 `완료` + 완료 조건의 마무리 실측 | 명세의 실측 기록, 진행판 | 부모 |
| T7 | 단계 `검증` → `구현` | 자동 검증 또는 실측 실패, 원인이 구현 결함 (§4 실패 분류) | 진행판 메모: 실패 내용 · 원인 분류 · 날짜 | 부모 |
| T8 | (어느 상태든) → `초안` | 명세 결함: 명세대로 만들었는데 틀렸거나 모자람 (예: 명세에 적은 문구가 80칸에서 줄바꿈) | 명세 `정할 것` 에 항목 추가. 영향받는 단계만 `예정` 으로 | 부모 · harness-engineer. 다시 T2 (사용자 재승인) |
| T9 | `완료` → `구현` (재개) | 회귀 발견. **고치기 전에** 회귀를 잡는 테스트를 더하고 지금 코드에서 실패하는 것을 확인 | 진행판 메모: 회귀 내용 · 실패하는 테스트 이름 | 부모 → 담당 |
| T10 | (어느 상태든) ↔ `보류` | 사용자가 멈추거나 다시 요청 | 진행판 메모: 날짜 · 사용자 요청 요지 | 부모 |

- 하지 않는 전이: `초안` → `구현` (승인 없이 구현), 실측 기록 없는 `완료`, 테스트를 약하게 고쳐서 하는 T4.
  테스트의 검사를 빼거나 바꿨으면 그 검사가 덮던 것을 어디서 덮는지 보고에 적는다.
- 커밋과 설치본 반영은 상태가 아니다. 사용자 요청으로만 하므로 진행판의 `커밋` · `설치본` 열에 따로 둔다 (`안 됨` / 커밋 해시 / 반영 날짜).
  `완료` 는 커밋을 요구하지 않는다 (§9 D6). 대신 부모는 세션을 마칠 때 `커밋: 안 됨` 과 `설치본: 안 됨` 인 행을 사용자에게 한 번에 알린다.
- 미커밋 항목이 둘 이상이면 진행판 메모에 항목별 파일 목록을 둔다 (나중에 항목별로 커밋을 나눌 수 있게).

## 3. 진행판

- 위치: `docs/dev-board.md` 하나. 사용자와 모든 에이전트가 같은 파일을 본다. Claude 개인 메모리는 진행판으로 쓰지 않는다 (다른 에이전트가 못 본다).
- 내용: 명세 표(한 행 = 명세 단위), 단계 표(한 행 = 구현 순서의 한 줄), 항목별 메모(대기 · 실패 · 미커밋 파일), 회고.
- 명세 머리에는 진행판 행을 가리키는 한 줄만 둔다. 상태를 두 곳에 쓰지 않는다 (§9 D1).
- 고치는 사람: 부모 (담당 에이전트의 보고를 받아서). 에이전트끼리 같은 파일을 동시에 고치지 않게 한다 (§9 D2). harness-engineer 는 점검을 맡았을 때 고칠 내용을 보고하고, 부모가 맡기면 직접 고친다.
- 검사: `./runtime/node/node.exe tests/board-check.mjs` (새로, §8) 가 형식과 증거를 확인한다.
  - FAIL: 정해진 상태 이름이 아님 · ID 중복 · 단계 ID 의 앞부분이 명세 표에 없음 · `완료` 단계에 실측이나 증거가 없음 · `완료` 명세에 완료가 아닌 단계가 있음 · 없는 커밋 해시 · 없는 문서 경로 · `docs/*-spec.md` 인데 진행판에 없음
  - WARN: `승인` 이후인데 승인 날짜 기록이 없음 · 명세가 `초안` 인데 `구현` · `검증` 단계가 있음
  - 증거가 충분한지(캡처가 요구한 창 크기인지 등)는 검사가 판단하지 못한다. harness-engineer 의 점검이 본다.

## 4. 작업 루프

하위 에이전트는 다른 에이전트를 부르지 못하므로 루프는 부모를 거쳐 돈다.

```
진행판에서 다음 행 선택 → 넘김 → 담당 작업 · 자동 검증 → 돌려받음 → 진행판 기록
   ↑                                                          │
   └── 실패 분류에 따라 되돌림 · 사용자 결정 요청 · 회고 ←──────┘
```

### 부모의 순서

1. 진행판에서 `대기` 가 없는 행 중 다음에 움직일 사람이 부모나 에이전트인 것을 고른다. `대기` 가 사용자인 것은 모아서 사용자에게 묻는다 (선택지와 권장안).
2. 넘기기 전에 공유 자원(아래 표)이 겹치는 검증이 실행 중인지 본다. 겹치면 넘김 내용에 "실행하지 말 것"을 적거나 순서를 미룬다.
3. `.claude/rules/delegation-rule.md` 와 아래 "넘김과 보고" 에 따라 맡긴다.
4. 돌려받으면 진행판을 고치고 (상태 · 자동 검증 · 실측 · 증거), 실패면 분류에 따라 되돌린다.
5. 단계를 마치면 회고를 한 줄 이상 남긴다 (§5). 반복된 실수가 있으면 harness-engineer 에게 규칙화를 맡긴다.
6. 세션을 마칠 때 사용자에게 알린다: 사용자 결정 대기, `커밋: 안 됨`, `설치본: 안 됨`.

### 넘김과 보고

무엇을 넘기고 결과를 어떻게 검토하는지는 [`.claude/rules/delegation-rule.md`](../.claude/rules/delegation-rule.md) 가 기준이다 (D10).
이 절은 그 위에 진행판에 남기기 위해 더하는 것만 정한다.

넘길 때 더하는 것
- 진행판의 단계 ID (`<id>/<n>`)와 그 단계의 확인 방법 (명세의 구현 순서 줄).
- §6 의 자동 검증 명령과, 허락되지 않은 승인 지점 (커밋 · push · 릴리스 · 실제 설치본 · 과금 LLM · 사용자 터미널과 마우스 · 되돌리기 어려운 삭제는 기본적으로 안 됨).
- 지금 실행 중인 검증과 그것이 쓰는 공유 자원 (아래 표).

보고에서 진행판으로 옮기는 것 (에이전트 정의의 "보고" 절이 이 항목을 요구한다)
- 자동 검증: 명령 이름 · 결과 줄 · 기준 (`HEAD <해시>` + 미커밋 여부).
- 실측: 무엇을 어떻게 했는지 · 결과 · 캡처와 로그 경로 · 확인하지 못한 것 (터미널 종류 · 창 크기 · 실제 모델).
- 실패: 내용 · 아래의 원인 분류 · 제안하는 되돌릴 상태.
- 뺀 검사: 테스트에서 빼거나 바꾼 검사와 그 대신 덮는 곳.
- 확인한 것과 추측: 실행하거나 읽어서 확인한 것과 추측을 나눠 쓴다. 추측에는 확인 방법을 붙인다.

- 분류가 갈리면(명세 결함인지 구현 결함인지) 부모가 사용자에게 선택지로 묻는다.

## 5. 개선 루프

### 회고

단계를 마칠 때(완료 · 실패 · 보류 모두) 진행판의 회고 절에 날짜와 단계 ID 로 짧게 남긴다.

```
- <날짜> <id>/<단계>: 예상과 달랐던 것 · 사람이 지적한 것 · 반복된 실수(몇 번째인지) → 조치 또는 "만들지 않음: <이유>"
```

### 규칙으로 만드는 기준

- 두 번 이상 반복된 실수, 또는 한 번이라도 피해가 큰 것(키가 파일 · 로그에 남음, 되돌리기 어려운 삭제, 사용자 화면을 건드림)은 규칙으로 만든다.
- 다음 순서로 고른다. 위의 것이 가능하면 아래 것으로 대신하지 않는다.

| 순서 | 형태 | 언제 | 확인 |
| --- | --- | --- | --- |
| 1 | 테스트 · 검사 스크립트 | 기계적으로 판정할 수 있으면 | 고치기 전 상태에서 실패하고, 고친 뒤 통과하는 것을 보인다 |
| 2 | 에이전트 정의의 규칙 (`.claude/agents/*.md` 의 해당 절) | 판단이 필요한 작업 습관 | 정의끼리 문구 · 명령이 같은지 |
| 3 | 명세의 확정 사항 | 제품 동작 · 화면 규칙 | 사용자 승인 (T2) |
| 4 | §7 함정 목록 | 환경의 사실 (Windows · Git Bash · ConPTY · psmux) | 실측 날짜와 확인 명령 |

- 규칙화도 과정 변경이므로, 1 은 harness-engineer 가 직접 만들어 보고하고, 2 · 3 은 문서 초안을 만들어 부모를 거쳐 승인받은 뒤 적용한다.
- 만들지 않기로 한 것도 이유와 함께 회고에 남긴다 (같은 것을 다시 논의하지 않게).
